# Allocation WASM Example

This example demonstrates how to build and use a WebAssembly (WASM) plugin that runs as part of an Agones `GameServerAllocation`, using the [Extism PDK for Go](https://github.com/extism/go-pdk).

A WASM plugin provides a way to run custom logic against the `GameServer` that has been selected for allocation, as part of the same update that allocates it.

> This is an Alpha feature, and requires the `WasmAllocation` feature gate to be enabled.

## Overview

The example is a multi-session `GameServer`: each `GameServer` hosts up to three sessions, each session has its own port, and the port is named after its session. A `freeSessions` List on the `GameServer` holds the sessions that are not in use.

The plugin exports two WASM functions:

- **allocate**: Removes the first session from the List, and stores it in an annotation on the `GameServer`. Since the `GameServer` annotations are returned from an allocation, the caller knows which session, and therefore which port, it has been given.
- **allocateNone**: A no-op example function that returns the `GameServer` without changing it. This demonstrates how to export multiple functions from a single WASM module.

`allocate` is configured with the following config values:

| Config       | Description                                        | Default   |
|--------------|----------------------------------------------------|-----------|
| `list`       | The List to take a session from. Required.         |           |
| `annotation` | The annotation that the session is stored under.   | `session` |

### How it works

The plugin function is passed the `GameServer` that was selected for allocation as JSON, after any metadata and Counter or List actions on the `GameServerAllocation` have been applied to it. It returns the `GameServer` as JSON, with any changes it wants to make.

A few things to be aware of when writing a plugin:

- The whole `GameServer` that is returned replaces the `GameServer`. Return everything that was passed in, not only the fields that were changed. This example works with the `GameServer` as generic JSON for this reason, so that no fields are lost.
- The `GameServer` is always `Allocated`, and its name, namespace, uid and other identifying metadata cannot be changed. Changes to these are ignored.
- If the plugin returns an error, the allocation fails, and the `GameServer` is not changed.
- The `GameServer` is updated once, with the allocation and the changes from the plugin together. If two allocations pick the same `GameServer` at the same time, only one succeeds, so a session cannot be given out twice.

### Installing extism CLI

If you don't have the extism CLI installed, you can use the Agones build environment which includes it:

```bash
cd ../../build
make shell
```

This will drop you into a shell with the required extism CLI and Go version available in the PATH.

## Files

- **main.go**: The WASM plugin implementation using github.com/extism/go-pdk
- **Makefile**: Convenience targets to build and locally test the WASM module
- **fleet.yaml**: Example multi-session Fleet
- **gameserverallocation.yaml**: Example GameServerAllocation that uses the WASM plugin
- **plugin.wasm**: Pre-built WASM binary (generated by `make build`)

## Building the WASM Plugin

To compile the WASM plugin:

```bash
make build
```

This produces `plugin.wasm` in the current directory using the WASI target:
```bash
GOOS=wasip1 GOARCH=wasm go build -buildvcs=false -buildmode=c-shared -o plugin.wasm
```

## Testing Locally

To test the plugin locally with a sample `GameServer`:

```bash
make test
```

This runs the `allocate` function with a minimal `GameServer` JSON input using the extism CLI. The `GameServer` has three free sessions, so the output should show `session-1` stored in the `session` annotation, and `session-2` and `session-3` left in the `freeSessions` List.

### Testing with custom arguments

You can override the test arguments by supplying `ARGS`. For example, to store the session in a different annotation:

```bash
make test ARGS='--config annotation=my-session'
```

## Deploying to Kubernetes

### Step 1: Create the Fleet

```bash
kubectl apply -f fleet.yaml
```

### Step 2: Allocate a session

```bash
kubectl create -f gameserverallocation.yaml -o yaml
```

The `status.metadata.annotations` of the result has the `session` that was allocated, and `status.ports` has the port with the same name.

Run the allocation again, and the same `GameServer` is returned with the next session, until all three sessions are in use, at which point the next `GameServer` is allocated.

When a session ends, the game server adds it back to the List through the Agones SDK, which makes it available to be allocated again.
